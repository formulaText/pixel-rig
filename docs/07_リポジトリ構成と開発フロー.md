# リポジトリ構成と開発フロー

TypeScript＋Vite＋npmを採用。依頼者はiPhone SafariでCodexとGitHubを利用する。手元のターミナル操作は不要。
開発・コード管理・ビルド・配信はGitHubのサービスで完結する。公開リポジトリ formulaText/pixel-rig、GitHub Actions、GitHub Pagesを使用し、外部ホスティングと認証画面は導入しない。プロジェクトのライセンスは保留。

## 実装範囲

V6-01は最小起動ページと配信基盤（PR #3、実機確認・昇格済み）。V6-02は研究アプリへのv5移植（原本相当の再現確認として区切る依頼者判断。PNG保存未達は保留、色のちらつきは未解決）。r128で分割・v5再現（V6-02）→別PRでThree.js更新→描画基盤の拡張の順序を守る。
原本はprototypes/、現行説明はdocs/、作業指示はdocs/issues/。原本HTML・references/・archive/original-documents/は変更しない。

Node 24.22.1（.nvmrc）、npm 11.9.0、three 0.128.0を固定。直接依存も完全な版番号とし、package-lock.jsonを登録。CIではnpm ci→原本照合→型検査→ビルド→配信構成テストを実施する。GitHub Actions自体もコミットSHAで固定する。
開発者向けコマンドは `npm ci`、`npm run check`、`npm run dev`。ローカル起動は研究アプリ単体。配信入口を含む確認には `node scripts/site.mjs` で work/site/ を構築し、HTTPサーバーで配信する。ローカルのIDはlocal-で始まり、未コミットの変更を含み得るため実機承認には使用しない。

## 2系統を保持する配信構成

|公開パス（/pixel-rig/の下）|内容|
|---|---|
|index.html|入口。確認済み版／検証候補／原本v5と各識別情報|
|stable/|依頼者が実機確認し明示承認した成果物。初回は「未確定」の案内|
|candidate/|最新の検証候補1件。更新時にこの系統だけを置換|
|original/v5.html|配布時とバイト一致する原本v5|
|site.json|両系統のビルドID・元コミット・ファイルハッシュ、原本と承認の記録|

永続保存先は同一GitHubリポジトリの `pages-state` ブランチ。保持対象はstableとcandidateの2系統であり、PRごとのディレクトリやプレビューは作らない。Gitの変更履歴は残るが、過去の候補を公開する入口は作らない。Actionsの一時artifactは受け渡し用（候補は1日保持）で、期限切れしても確認済み版は失われない。

候補更新は保存済みサイトを取得し、確認済み版のハッシュを検証した後、candidateだけを置換する。入口と原本とstableを含めた**サイト全体**を1つのPages artifactにして配信する。既存状態の取得失敗・破損時は停止し、空の確認済み版へ戻さない。
昇格は再ビルドせずcandidateの全バイトをstableへコピーする。ビルドIDも元コミットも保持し、実機で見た内容と対応させる。入口で系統を区別し、研究アプリ内には共通のビルドID・元コミットを表示する。成果物のbuild.jsonは各ファイルのSHA-256を記録し、JavaScript中のID・コミットも照合する。
Viteの `base: './'` と相対リンクにより、同じ成果物を `/pixel-rig/candidate/` と `/pixel-rig/stable/` で使用できる。V6-02はThree.js本体とGLSL文字列をJSに含め、模様・顔・アイコン・デカールは元データから実行時に生成する。研究アプリの実行にCDN参照はない。将来のアセットもViteのimportまたは相対URLを使う。

研究アプリはnpm依存を成果物へ含める。原本v5だけは既存の外部CDN（cdnjsのThree.js r128）参照を保持する。これは原本保全の例外であり、GitHub以外のビルド・ホスティング導入ではない。原本のSHA-256と登録コミットは入口側に表示し、原本HTMLへ追記しない。

## 初回の準備（iPhone Safari）

1. V6-01のPRを開き、「Checks」のCI成功と「Files changed」の内容を確認する。「Conversation」下部の「Merge pull request」→「Confirm merge」で依頼者がmainへ統合する。これはワークフロー登録であり、実機承認・確認済み版への昇格ではない。自動マージは設定しない。
2. リポジトリの「Settings」→「Pages」→「Build and deployment」の「Source」を「GitHub Actions」にする。メニューが見えない場合はSafariのページメニューから「デスクトップ用Webサイトを表示」。既にGitHub Actionsなら変更不要。
3. 「Actions」→「Pages - candidate or promote」→「Run workflow」で下記の候補更新を行う。workflow_dispatchは初回にmainへ登録する必要があるため、この順序とする。

## Run workflowフォームのiPhone Safari注意点

モバイル表示で「Run workflow」を押すと承認チェックだけが切り替わり、実行できない症状が依頼者の環境で発生した。Safariのページメニューから「デスクトップ用Webサイトを表示」に切り替えると実行できた。原因は未確定。候補更新・昇格のどちらも、このフォームで支障があればデスクトップ表示を使う。候補公開ではiphone_approvedを未チェックへ戻し、operationとsource_refを再確認してから実行する。実行一覧に新しいRunが出たことを確認し、連打しない。

## 候補の更新（承認不要の検証候補公開）

1. 「Actions」→「Pages - candidate or promote」→「Run workflow」。上部の「Use workflow from」は必ず **main**。
2. operationは **candidate**、source_refは **main**（別ブランチを確認するときだけそのブランチ名または完全コミットSHA）。expected_build_idは空、iphone_approvedは未チェックのまま「Run workflow」。PRごとの自動公開やpush時の自動公開は行わない。
3. 一覧に出た実行を開き、buildとpublishの緑のチェックを確認。「Summary」の公開リンクから開く。通常URLは https://formulatext.github.io/pixel-rig/ （設定後の実URLはGitHubの表示を正とする）。入口のcandidateビルドIDをSummaryと照合し、「検証候補」を開いてアプリ内のID・コミットも確認する。
4. 入口、候補、原本、確認済み版の各リンク、縦横変更、再読み込みを確認する。初回の確認済み版は「未確定」、比較先は原本v5。V6-01ではv5再現・ドラッグ移動・fpsの測定はまだ要求しない。

## 確認済み版への昇格（依頼者の実機確認後のみ）

1. iPhone 17 Safariで対象候補を確認し、入口または候補ページのビルドIDをコピーする。確認結果をIssue／PRへ記録する。
2. 同じ「Run workflow」で「Use workflow from」は **main**、operationを **promote**、expected_build_idへそのIDを貼り付ける。iphone_approvedの「実機で確認し…明示承認する」を依頼者本人がチェックし、実行する。source_refは使わない。
3. publishの成功後、公開入口の確認済み版と候補のID・元コミットが一致し、確認済み版が同じ内容を開くことを確認する。

依頼者本人（現在のリポジトリ所有者formulaText）の実行、承認チェック、現在の候補とのID一致を必須にする。候補が確認後に更新されていた場合は昇格を拒否する。新しい候補を改めて確認する。組織所有へ移管する場合は承認者の扱いを別途見直す。

## 失敗と並行操作

候補更新・昇格は共通concurrencyで直列化し、実行中の配信を後の操作でキャンセルしない。GitHubの待機枠は新しい実行で置換され得るので、連打せず先の実行完了を待つ。状態ブランチは通常のfast-forward pushだけを使い、外部更新と競合したら停止する。
状態保存後にPages配信が失敗した場合、公開サイトは旧版、pages-stateは次に配信する版になり得る。成功するまで公開済みとは扱わない。失敗した実行で「Re-run failed jobs」を選ぶと保存済み状態を再取得してサイト全体を再配信する。全ジョブ再実行では候補のビルドIDが変わるため実機確認もやり直す。別操作が間に入った場合は最新の候補IDを再確認する。
Pages設定・github-pages環境の制限・Actionsの書き込みポリシーにより失敗したときはログを確認する。mainの実行を許可し、contents:writeでpages-stateへ書けることが必要。PATや外部サービスの認証情報は不要。pages-stateを削除したり手編集したりしない。
