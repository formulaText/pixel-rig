# リポジトリ構成と開発フロー

TypeScript＋Vite＋npmを採用。依頼者はiPhone SafariでCodexとGitHubを利用する。手元のターミナル操作は不要。
開発・コード管理・ビルド・配信はGitHubのサービスで完結する。公開リポジトリ formulaText/pixel-rig、GitHub Actions、GitHub Pagesを使用し、外部ホスティングと認証画面は導入しない。プロジェクトのライセンスは保留。

## 実装範囲

V6-01は最小起動ページと配信基盤（PR #3、実機確認・昇格済み）。V6-02は研究アプリへのv5移植（原本相当の再現確認として区切る依頼者判断。PNG保存未達は保留、色のちらつきは未解決）。r128で分割・v5再現（V6-02）→別PRでThree.js更新→描画基盤の拡張の順序を守る。
原本はprototypes/、現行説明はdocs/、作業指示はdocs/issues/。原本HTML・references/・archive/original-documents/は変更しない。

Node 24.22.1（.nvmrc）、npm 11.9.0、three 0.128.0を固定。直接依存も完全な版番号とし、package-lock.jsonを登録。CIではnpm ci→原本照合→型検査→ビルド→配信構成テストを実施する。GitHub Actions自体もコミットSHAで固定する。
開発者向けコマンドは `npm ci`、`npm run check`、`npm run dev`。ローカル起動は研究アプリ単体。配信入口を含む確認には `node scripts/site.mjs` で work/site/ を構築し、HTTPサーバーで配信する。ローカルのIDはlocal-で始まり、未コミットの変更を含み得るため実機承認には使用しない。

## 2系統を保持する配信構成

|公開パス（/pixel-rig/の下）|内容|
|---|---|
|index.html|入口。確認済み版／検証候補／原本v5と各識別情報|
|stable/|依頼者が実機確認し明示承認した成果物。初回は「未確定」の案内|
|candidate/|最新の検証候補1件。更新時にこの系統だけを置換|
|original/v5.html|配布時とバイト一致する原本v5|
|site.json|両系統のビルドID・元コミット・ファイルハッシュ、原本と承認の記録|

永続保存先は同一GitHubリポジトリの `pages-state` ブランチ。保持対象はstableとcandidateの2系統であり、PRごとのディレクトリやプレビューは作らない。Gitの変更履歴は残るが、過去の候補を公開する入口は作らない。Actionsの一時artifactは受け渡し用（候補は1日保持）で、期限切れしても確認済み版は失われない。

候補更新は保存済みサイトを取得し、確認済み版のハッシュを検証した後、candidateだけを置換する。入口と原本とstableを含めた**サイト全体**を1つのPages artifactにして配信する。既存状態の取得失敗・破損時は停止し、空の確認済み版へ戻さない。
昇格は再ビルドせずcandidateの全バイトをstableへコピーする。ビルドIDも元コミットも保持し、実機で見た内容と対応させる。入口で系統を区別し、研究アプリ内には共通のビルドID・元コミットを表示する。成果物のbuild.jsonは各ファイルのSHA-256を記録し、JavaScript中のID・コミットも照合する。
Viteの `base: './'` と相対リンクにより、同じ成果物を `/pixel-rig/candidate/` と `/pixel-rig/stable/` で使用できる。V6-02はThree.js本体とGLSL文字列をJSに含め、模様・顔・アイコン・デカールは元データから実行時に生成する。研究アプリの実行にCDN参照はない。将来のアセットもViteのimportまたは相対URLを使う。

研究アプリはnpm依存を成果物へ含める。原本v5だけは既存の外部CDN（cdnjsのThree.js r128）参照を保持する。これは原本保全の例外であり、GitHub以外のビルド・ホスティング導入ではない。原本のSHA-256と登録コミットは入口側に表示し、原本HTMLへ追記しない。

## 日常の担当と承認

依頼者は研究方針の選択、iPhoneでの見た目・操作感・fps確認、採用判断を担当する。Codexは実装、検査、Issue・PR管理、候補公開、Actionsと公開結果の確認、資料更新を担当する。描画変更のマージと確認済み版への昇格は、対象ビルドの明示承認後にCodexが代行する。マージボタンやRun workflowを毎回依頼者に操作させない。技術検査の成功は実機確認・採用承認ではない。

ChatGPT相談は自動取得できない。依頼者からCodexへ渡された承認を根拠とし、受領した承認原文・受領日時と文脈（またはURL）をPRコメントに残す。秘密情報や相談全文を公開せず、必要な承認部分のみ転記する。例：

> ビルド `<対象ビルドID>` をiPhoneで確認済み。採用し、対応する描画PRのマージと確認済み版への昇格を承認します。Codexで実行してください。

マージだけ／昇格だけの承認ならその範囲だけ実行する。承認後に候補が変わった場合は別ビルドを昇格せず停止する。再ビルドしてIDを合わせず、確認したcandidateの全バイトをstableへコピーする。

## Codexによる候補公開

既存の `Pages - candidate or promote`（pages.yml）を再利用する。現在のGitHub接続はPR作成・マージ・コメント・Actionsジョブ確認が可能だが、新規workflow_dispatchの専用ツールがない。そのため、同じリポジトリの対象PRへ**新規コメント**を投稿して起動できる。編集・通常のコメント・Issueのみへのコメントは実行しない。マージ後のPRにも投稿可能。外部サービス・追加管理画面・PATは不要。

1. 最新main・対象PR/Issue・pages-stateと公開結果を読み、完了済み操作を除外する。公開対象は完全コミットSHAで指定することを推奨。
2. Codexが対象PRへ次の1行を投稿する（例のSHAを実在する対象SHAに置換）。

```text
/pixel-rig-pages {"operation":"candidate","source_ref":"<完全コミットSHA>","executor_label":"Codex"}
```

3. GitHub Actionsの `request` → `build` → `publish` の結果を確認する。mainのコードで要求を検証し、候補のコードは書込み権限のないbuildジョブでのみ実行する。
4. publishは変更前の公開状態と保存状態を照合し、候補だけを更新する。配信後にも公開 `site.json`、両系統の `build.json` と全配信ファイル、入口・原本のハッシュを照合する。最終検査の成功と実際の公開ビルドIDを確認して報告する。ログのJSONはURL・stable/candidate ID・原本ハッシュ・照合数を含む。
5. URL・対象ID・変更点・必要な実機確認・次の行動を短く報告する。運用のみの変更なら描画の全面再検証を求めず、必要な確認は入口から候補と確認済み版を開けることに限定する。

## 承認後の昇格代行

Codexが受領済み承認を対象PRへ次の形式で記録・実行する。これは書式例であり実際の承認ではない。`approval_text` は対象IDを含む受領原文、`approval_source` は承認元URLまたはCodexへの依頼日時・文脈。`iphone_approved` は実機確認・昇格承認を受領した場合にだけtrueにする。

```text
/pixel-rig-pages {"operation":"promote","expected_build_id":"<実機確認したビルドID>","iphone_approved":true,"approval_by":"formulaText","approval_text":"ビルド <実機確認したビルドID> をiPhoneで確認済み。確認済み版への昇格を承認します。","approval_source":"Codexへの依頼 YYYY-MM-DD HH:mm JST／対象PRと承認文の受領","executor_label":"Codex"}
```

承認者は個人リポジトリ所有者formulaText。実行者（GitHub認証名）は所有者、またはリポジトリ変数 `PAGES_EXECUTORS` に明示登録されたアカウントのみ。既定は空で、全write権限者へ広げない。必要な場合だけ所有者が Settings → Secrets and variables → Actions → Variables → New repository variable で、名前 `PAGES_EXECUTORS`、値は委任するGitHub名のカンマ区切りを設定する。現在の接続はformulaTextとして実行するので追加設定不要。`executor_label: Codex` により同じGitHub名でも代行経路を区別する。再実行者も同じ許可対象に限定する。組織移管時は停止し承認者設計を見直す。

これは許可された実行者による承認受領の記録であり、ChatGPTの自動読取や依頼者の電子署名ではない。実行者が承認を捏造してよい仕組みではない。型・承認フラグ・所有者名・対象ID・原文内のID・受領元を検査し、現在候補とのID一致を状態更新直前にも確認する。

`site.json.approval` に承認者、実行者、再実行者、実行経路、ビルドID、承認原文・受領元、要求コメントURL、Actions URL、時刻を保存する。旧承認は書換えず保持する。`lastOperation` とpages-stateのGit履歴・Actionsログから候補公開も追跡できる。昇格ではbuildを実行せず、保存済みcandidateをそのままstableへコピーして一致を検査する。

## 手動フォーム（接続障害時のみ）

初回main登録とPagesのSource=GitHub Actionsは完了済み。日常の本人操作は不要。Codex側の接続を復旧できず本人操作が必要な場合だけ、iPhone Safariで Actions → Pages - candidate or promote → Run workflow → Use workflow from=main と案内する。

- 候補：operation=candidate、source_ref=対象SHA、iphone_approved=false、承認欄は空。
- 昇格：operation=promote、expected_build_id=実機確認したID、iphone_approved=true、approval_by=formulaText、approval_text=ID入り承認文、approval_source=承認元、executor_label=GitHub。Codexが代行する場合はCodex。
- 緑のrequest/build（昇格は省略）/publishと公開IDの一致が完了表示。モバイルフォームで支障がある場合だけSafariの「デスクトップ用Webサイトを表示」を使い、連打しない。原因は未確定。

秘密情報をチャットへ貼り付けさせない。Pages設定・環境保護・Actions権限など所有者にしか変更できない設定が障害であることを確認してから、その設定と最小の操作だけを依頼する。

## 失敗と並行操作

認可済み要求の状態取得・変更・保存・配信・公開照合はpublishの共通concurrencyで直列化し、実行中の配信をキャンセルしない。候補のbuildは並列になり得る。通常のPRコメントや拒否された要求は配信の待機枠を使わない。GitHubの待機枠は新しい配信で置換され得るので、Codexは先の配信完了を待って次を起動し、要求順が配信順になるとは仮定しない。状態ブランチはfast-forward pushのみで、外部更新と競合したら停止する。

状態保存後にPages配信が失敗すると公開サイトは旧版、pages-stateは次に配信する版になり得る。成功するまで公開済みと扱わない。同じ実行の失敗ジョブ再実行では変更前の公開照合を省略し、最新保存状態を再取得して、対象IDを再照合し同じ候補artifactから再配信する。全ジョブ再実行は候補IDが変わる。artifact期限切れなら候補を新しく公開し、旧承認を新IDへ流用しない。別操作が間に入った場合は最新状態を読み直す。新しい実行で公開と保存状態の不一致が見つかった場合は、先の配信失敗を解消する。

Pages設定・github-pages環境・Actions権限により失敗した場合はログを確認する。mainの配信処理に既存の contents:write / pages:write / id-token:write が必要。読取りだけのrequest/buildへ書込み権限を追加しない。pages-stateを削除・手編集しない。
